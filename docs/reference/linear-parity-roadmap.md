# Linear Enterprise parity audit and roadmap

## Implementation update — October 13, 2026 (comment collaboration)

Issue comments now support replies, root thread resolution and reopening, author-only editing and deletion, and member emoji reactions in the browser and MCP. Replies notify thread participants as well as issue subscribers. All actions use team authorization, optimistic versions, audit entries, and issue activity events. Mentions, rich text editing, and full notification preferences remain open.

## Implementation update — October 13, 2026 (issue activity)

Issue changes now record structured before/after values in the existing event log. The issue detail shows a permission-checked, paginated history, including Triage and integration changes. Claude Code can read the same history through `list_issue_activity` and manage its own issue subscriptions. This advances the Phase 1 issue lifecycle and Phase 3 MCP surface.

## Implementation update — October 13, 2026

Team issue statuses now have persisted per-team names, categories, default state, order, and management controls. Issue and template writes validate against their team’s configured statuses; renames and deletions migrate existing records. Issue lists, board columns, filters, dashboards, completion metrics, and GitHub status automation use the configured workflow. A local migration and API test covered create, rename, delete/replacement, validation, and issue propagation. This advances Phase 1 workflow configuration but does not complete Phases 1–3.

## Implementation update — October 12, 2026

The first build pass added validated issue dates, estimates, parent and related links, project milestones and dependencies, project updates, initiative hierarchy, issue templates, bulk status/priority edits, compound custom views, documents, customers and requests, release pipelines/releases, and search/navigation for several new record types. A connected GitHub repository can now create a completed release on a configured continuous pipeline branch. MCP tools now expose the new document, customer, request, release, pipeline and template records in addition to expanded issue/project/initiative fields. The corresponding browser and MCP actions use the same authenticated record API and audit path as existing features. Local API checks exercised create/read/validation/export and uninvited-user denial.

This is **partial implementation**, not completion of Phases 1–3. The new records still live in the single-workspace JSON store. Rich editing, configurable team statuses, server-side query/search at scale, event-driven collaboration, full Triage/Asks, Insights, AI workflows, public API/OAuth/webhook platform, and complete provider integration matrices remain open. Slack, GitHub and Notion are not live until developer apps and credentials are configured; Notion native previews also require partner approval. A paid Linear Enterprise tenant and multiple clone tenants are needed for the acceptance flows below.

Audited October 12, 2026. Target: functional and workflow parity with the current Linear Enterprise product, including the customer-facing app, integrations, API/MCP access, and Enterprise administration. This is a **gap audit and implementation roadmap**, not a claim that parity has been reached.

## Method and limits

- I used two browser tabs side by side: the deployed rebuild and a signed-in `linear.app` workspace. I navigated issue lists, creation and detail menus, projects, views, search, inbox, team and workspace settings, API/webhook and integration settings, and the available administrative screens. I did not save changes in the real workspace or connect external providers.
- The signed-in Linear workspace is on the Free plan. Enterprise-only controls were visible in some settings but could not be exercised end to end. Those rows are corroborated with current [Linear pricing](https://linear.app/pricing) and the linked first-party documentation. A feature observed in a menu is not evidence its complete workflow was tested.
- I inspected the deployed rebuild and its current source, notably [`public/linear.js`](../public/linear.js), [`app/api/records/route.ts`](../app/api/records/route.ts), [`app/api/bootstrap/route.ts`](../app/api/bootstrap/route.ts), [`lib/workspace-server.ts`](../lib/workspace-server.ts), [`docs/integrations-setup.md`](integrations-setup.md), and [`docs/enterprise-scope.md`](enterprise-scope.md). The earlier [divergence audit](nonlinear-functionality-audit.md) tracks corrections already made; this document concentrates on remaining missing behavior.
- Evidence codes below: **U** = clicked or inspected in the signed-in Linear UI; **D** = current official Linear documentation; **C** = rebuild UI/source inspection. A row marked U/D/C has stronger coverage than D/C. Gated workflows still need a later test in an Enterprise tenant.

## Executive assessment

The rebuild has useful working foundations: authenticated member records, teams and permissions, issues with comments and attachments, projects, initiatives, generated cycles, Triage/Ask intake, saved preset views, inbox, dashboards, audit output, CSV export, partial Slack/GitHub/Notion integration code, and a 17-tool MCP surface. These are substantially narrower than Linear Enterprise. The most important gap is structural: the app currently stores a limited set of JSON record types in one workspace, with fixed issue statuses and only three saved-view predicates. Filling screens alone will not make advanced workflows or integrations function.

The live Site currently admits its owner only. The application can model multiple members, but customer access and workspace isolation are not yet equivalent to a multi-tenant SaaS. The separately deployed MCP gateway remains private; public external access was rejected by automatic approval review in prior work. Provider developer apps and credentials have not been supplied, so Slack, GitHub, and Notion are **not live connections**. [Integration setup and exact supported subset](integrations-setup.md) is the source of truth for those connectors.

## Build sequence and dependencies

**Phase 0 — Customer-ready foundation.** Introduce real workspace ids and tenant-bound authorization across every read, write, file and integration event; migrate existing `default` data; add invitation delivery and Site admission; establish a deployment identity model for Google Workspace SAML and SCIM. Replace the `LIMIT 5000` all-record bootstrap and 15-second polling with paginated queries, indexed search, and event-driven updates. Publish the public API/MCP boundary only after tenant isolation and token scope tests pass. This phase prevents later features from being built around a single shared record bag.

**Phase 1 — Complete core work.** Migrate issue/project/view JSON data into typed domain tables or validated entity structures with durable event history. Add team statuses, issue relations/subissues, dates/estimates/SLAs/recurrence, rich editor, templates, bulk actions, deep links and the shared filter/display engine. Add project milestones, dependencies, updates and timeline. This unlocks most daily user workflows and supplies the entities later integrations need.

**Phase 2 — Planning and operations.** Build documents, initiative hierarchy, richer cycles, customer records and requests, full Triage/Asks, releases, Insights/Pulse and the corresponding policies. Wire each feature into search, filters, activity, audit, API, MCP, export and permission checks at the time it ships.

**Phase 3 — Ecosystem and intelligence.** Configure and verify Slack, GitHub and Notion developer apps in test workspaces; close their feature matrices; add the public OAuth/API/webhook platform and a broader connector strategy. Add the in-app agent, Loops, coding/review workflows and Triage Intelligence using tenant-safe retrieval and audited tool execution. Provider availability and Notion partner approval are external dependencies.

**Phase 4 — Enterprise acceptance.** Run scenario-based comparison in a paid Linear Enterprise test tenant and in two or more clone customer tenants. Validate SAML/SCIM lifecycle, private-team access, retention, export/import, connected integrations, performance, accessibility, security review, operational support, and contracts. Do not use UI resemblance as the completion criterion.

## Acceptance flows for functional parity

Each flow must work through the browser, relevant public API/MCP operations, and permission boundaries, with audit events and stable URLs where applicable.

1. **Issue lifecycle:** Create from a template with rich text, labels, due date, estimate, parent, relation and attachment; comment/mention, subscribe, transition status, bulk edit, recover after deletion; another authorized user sees updates promptly.
2. **Team workflow:** Admin defines statuses/defaults and automation; member sends an issue to Triage; responsible user reviews, merges a duplicate or accepts it; generated cycle rollover and metrics reflect the result.
3. **Project delivery:** Create multi-team project with lead, priority, dates, milestones, dependencies, documents and updates; plan on timeline; issue changes roll up to milestone/project/initiative health.
4. **View sharing:** Save a compound filtered issue, project or initiative view at personal/team/workspace scope; another user sees only authorized records; favorites, notifications and URL state persist.
5. **Customer feedback and Asks:** A non-member submits via Slack/email/web; the conversation becomes an issue in Triage with customer attribution; replies sync both ways without revealing private issues.
6. **GitHub release path:** Install GitHub App, link branch/PR/commit/reviews to an issue, apply configured status transitions, associate shipped commits with a release and generate a changelog.
7. **Enterprise identity:** Invite user; Google Workspace SAML login and SCIM group assignment grant only intended teams; deprovisioning revokes app/API/MCP sessions and is audited.
8. **Developer access:** Customer creates scoped API key/OAuth app, receives signed webhooks with retry, uses Claude Code MCP for permitted read/write operations; private-team data stays inaccessible.
9. **Search and export:** Search across issues/projects/docs/customers including archived states; migrate a representative workspace with links and attachments; export and re-import without losing relationships.
10. **Agent/automation:** Agent answers with permission-filtered evidence, proposes or executes authorized mutations, supports review, and logs scheduled Loop actions and usage by workspace.

## Validation still needed

The Free Linear workspace had no representative populated projects, customer data, paid AI usage, or active integrations. Before declaring parity in any row, compare a populated Enterprise tenant with the clone using the same fixtures and roles. Validate keyboard and accessibility behavior, latency on large datasets, mobile/desktop behavior, notification delivery, conflict handling and data retention. Official docs establish scope; only end-to-end acceptance in both products establishes equivalent behavior.

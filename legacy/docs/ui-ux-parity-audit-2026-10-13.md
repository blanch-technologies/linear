# Linear versus clone: UI and workflow parity audit

Audited October 13, 2026 against the signed-in `linear.app/chuckscuts` workspace and the deployed private clone at `linear-workspace-rebuild.sleekbat64.chatgpt.site`. Both were inspected at a desktop browser viewport. I opened and compared issue lists, issue creation and detail, projects and project creation, views and filter creation, search, Inbox, My issues, team home, settings, team settings, and integrations. I inspected menus and forms without saving data in Linear. The Linear workspace is on a Free plan and has no projects; Enterprise-only behavior and populated project detail were not exercised. The workspaces contain different records, so this audit compares structure and interactions rather than text or counts.

## Assessment

The clone preserves the recognizable left rail, issue status groups, project table, property rail, and core navigation terms. It also has working versions of several behaviors that were previously missing, including configurable team issue statuses, issue activity, comment threads, project milestones and updates, and MCP operations. Yet the day-to-day experience is still visibly and functionally distinct. The largest switching costs are the global navigation model, issue detail as a modal instead of a routed page, plain text instead of rich editing, narrow search and filtering, compact project and view builders, and missing personal settings. These are interaction architecture gaps; changing colors alone will not resolve them.

The real workspace used a light theme set by the user's system preference. The clone uses a fixed dark presentation. Theme alone makes screenshots look far apart, but the geometry also differs: the clone has a longer, permanently expanded sidebar, large page headings and descriptions, taller rows, wider borders, and narrow, form-like modals. Linear uses a compact rail, smaller page headers, inline property pills, progressive disclosure, and large writing surfaces.

## Priority definitions

- **P0:** Common daily path feels materially different or cannot be completed with the same workflow.
- **P1:** A major secondary workflow or settings path differs.
- **P2:** Visual and interaction polish after the primary structure is aligned.

### Evidence boundaries and next live pass

- The Linear workspace contains only onboarding issues and no projects or active cycles. Populated project views, timeline planning, cycle rollover, triage processing and enterprise-only settings still need a controlled workspace with representative records.
- The clone contains seeded projects and cycles, so count and content differences are excluded from parity conclusions.
- Live provider integrations were not connected; this pass inspected setup surfaces only. A separate two-account/provider test is needed for Slack, GitHub, Notion, SSO/SCIM and delivery behavior.
- No real Linear issue, setting, template, cycle or recurring schedule was created or modified in this pass.

## Recommended implementation sequence

1. **Route and shell foundation:** real issue routes, back/forward restoration, dedicated settings shell, sidebar nesting, favorites and Agent placeholder only if a real Agent workflow is planned. This changes the navigation shape used by every later feature.
2. **Shared interaction primitives:** one command/action registry, menu/picker patterns, rich editor, keyboard selection, saved display options and permission-aware deep links. Use these in issue, project and view flows.
3. **Daily work surfaces:** issue composer/page/activity, server-backed search, list toolbar and custom view builder. Verify complete create → edit → find → comment → subscribe → navigate loops with two members.
4. **Project and team surfaces:** project composer/overview/timeline, team home and team settings. Connect existing milestone/dependency/update records to the same views and activity model.
5. **Visual calibration:** after both products use comparable themes and viewport sizes, tune typography, widths, row heights, spacing, icons, color tokens, hover/focus and motion. Capture a screenshot for each acceptance flow at desktop and mobile widths.

## Acceptance protocol for future passes

- Use the same viewport and theme on both sites, and compare equivalent data states (including empty and populated cases).
- For each surface test click, keyboard, direct URL, reload, back/forward, empty state, permission denied and narrow viewport behavior.
- Record a screenshot, route, interaction transcript, and pass/fail outcome for each acceptance flow.
- Use a paid Linear Enterprise workspace before claiming Enterprise-only parity. SAML/SCIM, governance, advanced integrations, and gated AI behavior were outside this live Free-plan comparison.
- Do not infer that a menu item is complete until its save/reload and second-member behavior has been observed.

This audit is a point-in-time comparison, not a claim of complete feature parity or an exhaustive test of every Linear plan feature. It should be read alongside [the broader functional roadmap](linear-parity-roadmap.md), which also tracks backend and Enterprise gaps.
